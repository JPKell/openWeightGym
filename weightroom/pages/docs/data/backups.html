Every new recovery archive requires age authenticated encryption. Servers hold public recipients; private recovery keys belong in separate recovery storage. Missing tools or recipients stop a backup before snapshots are taken. There is no unencrypted fallback.

  1. Install the distribution's age package on the front, on every compute node and on a trusted recovery computer. It supplies age and age-keygen. The main installer includes this dependency; existing installations need it added.
  2. Generate the key pair on the recovery computer using the first block below. Keep recovery.key on encrypted removable storage or in a private credential vault, with a second independent recovery copy. Keep it off application servers, source control, email and logs.
  3. Copy only recipients.txt to every machine: the front and each compute node. Each machine reads it from its own data folder, at DATA/backups/recipients.txt; Where recipients.txt goes gives the full path for each kind of installation and the commands. The file accepts 1–20 native age1… public recipients, one per line; any corresponding private key can decrypt the archive.
  4. Check each machine with the readiness command below, then open System → Backups, confirm the hosts are ready, create a set, and test it with the saved recovery key.
{% call doc_code('backup-key-generation') %} umask 077 age-keygen -o recovery.key age-keygen -y recovery.key > recipients.txt {% endcall %} {% call doc_note('warning', 'Keep the recovery key separate') %}

A lost private key cannot be reset or recovered by the server. Anyone obtaining it can decrypt retained archives addressed to it. A compromised service can still read live data, substitute future recipients or delete local backups.

{% endcall %} {% endcall %} {% call doc_section('Where recipients.txt goes', 'recipient-location') %}

Every machine backs up its own stores and encrypts them with the recipients in its own data folder. The front and each compute node therefore each need their own copy, at DATA/backups/recipients.txt, where DATA is that machine's data folder.

The data folder is the data setting in the machine's settings file, counted from the folder that holds the settings file. The front reads settings/weightroom.toml; a compute node reads settings/loadcoach.toml. Both are installed with data = "../data", so the data folder is the data folder beside settings in the installation folder. A copy anywhere else, such as settings/recipients.txt, is not read.

To confirm a machine's data folder, read the setting: grep '^data' /home/ACCOUNT/openWeightGym/settings/weightroom.toml on the front, or …/settings/loadcoach.toml on a compute node.

The file and its folder are checked before every backup. The backups folder must belong to the account that runs the services and is kept at mode 700. recipients.txt must be a regular file (not a link) owned by that account or root, and not writable by its group or others; use mode 600. Otherwise the backup stops with "Backup key/configuration permissions are unsafe".

{% endcall %} {% endcall %} {% call doc_section('Create and retain backups', 'recovery-sets') %}

System → Backups creates a shared set ID for front and compute. Scheduled backups use the same encrypted path. Each host snapshots every configured store: SQLite uses its online backup API; PostgreSQL uses pg_dump, a disposable restore, and content/schema comparisons. Missing or unreachable required stores fail that host's backup.

Compressed archive bytes stream directly into age. Before publication, the host decrypts the actual ciphertext with a disposable verification key, safely extracts it, and checks the embedded inventory, file hashes, SQLite integrity and counts. The temporary private key stays in memory and is discarded; only the encrypted archive and an owner-only sidecar manifest are published under data/backups/ID/. Creation and rotation are serialized locally.

Verified means the local creation-time check passed. It does not prove your saved private key works, that an offsite copy exists, or that the application has passed a recovery drill. Both halves must pass for a verified pair. Separate stores and hosts are not one distributed transaction; drain work and stop all writers before an offline backup if you need a coordinated snapshot.

Retention keeps 0–100 encrypted sets per host; zero keeps all. Rotation follows successful local publication. A partial pair does not stop retention advancing on the successful host, so allow enough sets for outages. External copies and legacy plaintext archives are managed separately.

Keep three copies across two independent storage systems, with one offline or immutable offsite copy. Copy both encrypted halves and their manifests to storage the application account cannot modify or delete, and save ciphertext hashes independently. Schedule backups for the data loss you can tolerate; test full recovery monthly and after key/storage changes. See CISA's encrypted, offline backup guidance.

{% call doc_note('note', 'Temporary plaintext and metadata') %}

Snapshots and verification files exist briefly inside private temporary directories. Use encrypted host/recovery disks and encrypted swap. Normal completion and handled errors remove temporary files; interruption may require administrator cleanup. Deletion does not guarantee secure erasure on SSDs or snapshots. The sidecar contains paths, hashes and counts, not raw credentials; it is operational metadata, not independent proof of provenance. The full manifest is also encrypted inside the archive.

{% endcall %} {% call doc_section('Verify and restore', 'restore') %}
  1. Choose a complete pair from before the failure or suspected compromise. Copy each host's archive.tar.gz.age to a trusted recovery computer with enough encrypted disk space. Obtain the matching private key separately. Supply --sha256 with the ciphertext hash from an independent trusted record when available.
  2. Run the verification command once per half. It authenticates the complete ciphertext before extraction and validates the embedded manifest and payload hashes. It rejects traversal, links, special files, duplicates and size-limit violations. It changes no live stores and removes temporary plaintext. The archive/extraction limit defaults to 1 TiB; adjust --max-bytes deliberately for larger installations.
  3. Add --output to stage files in a new private directory; existing directories are refused. Inspect its embedded manifest.json, original destinations, store engines and services to stop. Anyone holding a public recipient can create a new archive: use trusted backup storage and an independent ciphertext hash to establish provenance.
  4. For a drill, restore into an isolated installation with compatible application/schema versions. Restore PostgreSQL dumps into a fresh disposable database using compatible pg_restore, then check schemas and contents. The verifier checks dump hashes; it does not perform a new PostgreSQL server restore.
  5. For live recovery, drain work and stop every affected writer, worker, adapter, schedule and automatic restart. Preserve current databases and matching SQLite WAL/SHM files privately for rollback. Install only staged files mapped to reviewed destinations, with correct service ownership and mode 0600. Never combine restored SQLite files with old WAL/SHM files. Restore PostgreSQL into a fresh target and switch all owners together; never overwrite an active database.
  6. Recover long-lived credentials and model files separately. Start services and test password/authenticator sign-in, permissions, model inventory, conversations/media and benchmark evidence. Review restored grants and pending jobs before resuming schedules. Record the recovery-key and application checks in your existing operations record.
{% call doc_code('backup-verify') %} python -m loadcoach.backup_restore /recovery/front/archive.tar.gz.age \ --identity /private/recovery.key {% endcall %} {% call doc_code('backup-stage') %} python -m loadcoach.backup_restore /recovery/front/archive.tar.gz.age \ --identity /private/recovery.key --output /recovery/front-staged {% endcall %}

The installed suite-backup-verify command has the same interface. Its JSON report identifies the set, machine, ciphertext hash and whether PostgreSQL restore testing remains. A recovery-key test does not change the server's historical manifest.

{% call doc_note('warning', 'After a compromise') %}

Rebuild affected hosts from trusted software and use a known-clean backup. Before reconnecting, revoke restored API/job tokens, replace service/provider keys, reset affected passwords and re-enroll authenticators. Old backups can restore credentials or permissions revoked since they were created.

{% endcall %} {% endcall %} {% call doc_section('Planned reinstall', 'identities') %}

suite-identity creates a separate bundle of accounts, permissions, password verifiers, authenticator seeds, service credentials and configuration, excluding request/conversation history. It uses AES-256-GCM with a scrypt-derived key. Treat it as a master credential backup: use a unique randomly generated passphrase, store that separately, and keep the bundle offline or in immutable private storage.

Stop participating services, adapters, schedules and automatic restarts before export or applying an import. Imports preview first and refuse different existing accounts. This tool currently requires SQLite accounts and original installation paths. Test an isolated import before reinstalling. Use it for planned continuity; replace credentials after a compromise. See the identity export/import reference for commands and constraints.

{% endcall %} {% call doc_section('Older archives and key rotation', 'legacy') %}

Existing archive.tar.gz files remain plaintext. They are labeled legacy-unencrypted, excluded from protected recovery points and preserved outside automatic encrypted retention. New encryption does not protect old copies or filesystem snapshots.

Create and test an encrypted replacement before retiring an old recovery point. If historical data must remain, encrypt its old archive with age on a trusted machine, test decryption, and retain its original manifest. The offline tool accepts its embedded legacy schema, but manually wrapping an archive does not upgrade its server verification record. Remove plaintext copies and address snapshots under your storage policy after proving recovery.

For key rotation, generate a new private key off-server, replace public recipients on each host and test a new pair. Keep previous private keys separately while archives addressed to them exist. If a key is compromised, restrict access and re-encrypt retained data for a new key; rotation cannot protect ciphertext already stolen.
